# Dify Enterprise itself under GitOps

The product chart is installed by ArgoCD, like everything else in this
repository: Application `field-content-dify-chart`, created by the `dify`
component.

## Which chart

**Red Hat's certified `dify-enterprise` chart, from `https://charts.openshift.io`.**
It is public — no Dify credentials are needed to fetch it.

It is *not* Dify's public `dify/dify` chart (`https://langgenius.github.io/dify-helm`),
although both are version 3.9.8 and share most templates. Compared file by file,
the certified chart adds what OpenShift needs and the public one lacks:

| Only in `dify-enterprise` | |
|---|---|
| `openshift-routes.yaml` | The six edge-terminated Routes |
| `sandbox-rbac.yaml`, `unstructured-rbac.yaml`, `plugin-openshift-rbac.yaml` | SCC bindings |
| Five Secret templates written differently | |

The release running on this cluster reports `dify-enterprise-3.9.8` with
`charts.openshift.io` certification annotations. Installing `dify/dify` over it
would drop the Routes and the SCC bindings.

## The problem: the chart cannot reference a Secret

The chart renders every credential from its values. There is no
`existingSecret`. The passwords land in 11 Secrets — and, URL-encoded inside
Redis connection strings, in 5 ConfigMaps, one of them the gateway's
Caddyfile. So whatever renders the chart must know the passwords, and neither
ArgoCD nor Git should.

## How it is solved

1. **ArgoCD renders the chart with placeholders.** The values are the same as
   the `dify-values` ConfigMap (one shared template, `_values.tpl`): every
   credential is `@@secret:<name>/<key>@@`. Git and ArgoCD only ever see those.
2. **Every key that ends up carrying a credential is listed, with its content
   as a template.** `components/dify/files/secret-fields.yaml`, generated by
   `scripts/gen-dify-secret-fields.py` from the rendered chart: 33 keys in 17
   objects. The templates hold placeholders, never values.
3. **ArgoCD keeps the live value of those keys.** The Application lists them
   under `ignoreDifferences`, and `RespectIgnoreDifferences=true` makes a sync
   apply everything except them.
4. **A Job owns them instead.** `components/dify-chart-glue` — the
   Application's second source — runs `dify-chart-resolver` on every sync. For
   each key it fills the template from the data tier's Secrets
   (`dify-postgresql`, `dify-redis`, `dify-qdrant`, `dify-objectstorage`) and
   the cluster domain, and writes the result where it differs from what is live,
   then restarts Dify. So a fresh install gets its credentials, a new chart
   version gets its new templates, and a rotated password reaches every
   connection string that embeds it. On an install that is up to date it
   changes nothing. It may read only those four Secrets and patch only the 17
   objects.
5. **The database user name is written in plain text.** It is not a secret, and
   the chart copies it into ConfigMaps and a Deployment's env. Resolving it
   there would mean rewriting a Deployment behind ArgoCD's back.
   `components.dify.dbUsername` must match `prereqs.secrets.postgresqlUsername`;
   the Job fails loudly if it does not.

**Placeholders do not always appear as written.** The chart URL-encodes the
Redis password into connection strings, so there the placeholder reads
`%40%40secret%3Adify-redis%2Fpassword%40%40`, and the Job fills it with the
URL-encoded value. The generator recognises both forms and refuses anything
else that looks like a placeholder — the first version of it looked only for
`@@secret:`, reported "no placeholders elsewhere", and missed all six Redis
connection strings. A simulation of the sync against the live objects caught it
before anything was applied.

The same mechanism carries the plugin daemon's OTLP endpoints: the chart points
them at the collector's gRPC port, the daemon speaks HTTP only, and every export
fails (see [tracing.md](tracing.md)). They are listed with `:4318` as their
template. That used to be `scripts/fix-plugin-daemon-otlp.sh`, re-run by hand
after every `helm upgrade`.

### Verified before it was relied on

- **`RespectIgnoreDifferences` keeps a live value, including under `stringData`.**
  A throwaway Application over a Secret and a ConfigMap whose desired state held
  placeholders — in `data` and in `stringData` — and live objects holding real
  values. After the sync the ignored keys kept their live values, the others
  took the desired ones. One of the chart's Secrets uses `stringData`, which the
  API server merges over `data`, so both paths are listed for every Secret key.
- **The Job's templates reproduce the running deployment exactly.** A dry run
  (`DRY_RUN=1`) against the live namespace: all 33 keys, the Caddyfile included,
  computed from template plus cluster Secrets are byte-identical to what is
  running. With a wrong domain it reports the Caddyfile, so the comparison is
  real.
- **The Job's write path**, in a scratch namespace with fake credentials
  containing `/ + & : @ #` and a space: raw and URL-encoded placeholders both
  filled correctly (matching Go's `url.QueryEscape`), other keys untouched; a
  second run changes nothing; after rotating a source password only the objects
  embedding it are rewritten; a mismatched user name exits non-zero.
- **The sync itself**, simulated object by object with the ignore rules applied:
  no placeholder reaches the cluster, and the only differences are the ones
  listed below under "the switch".

## The switch (2026-09-26)

Taking over the running release, simulated beforehand against all 91 live
objects: 76 unchanged, and

| Change | Why |
|---|---|
| 11 Deployments' `checksum/*` annotations | The chart computes them from its values; the running ones date from before the hand-applied changes. Dify rolls once |
| `ENTERPRISE_OTEL_SAMPLING_RATE` 0.2 → 1.0 in 3 ConfigMaps | The repo's sampling rate; the hand-applied change had set only `OTEL_SAMPLING_RATE` |
| ServiceAccount `plugin-workload`'s `-dockercfg-` pull secret | The chart sets that SA's `imagePullSecrets` as a whole list; OpenShift adds its own entry back |

**Result.** ArgoCD synced at 16:49 UTC and Dify rolled once; healthy two
minutes later. All 91 objects kept their uid and carry ArgoCD's tracking
annotation; all 33 credential keys hash the same as before the switch; the
resolver Job, running under `restricted-v2`, found every key up to date and
changed nothing. The SA kept its pull secret, the helm test hook was not run.
Afterwards: the consoles answer, no authentication or connection error in any
component's log, and 200 traces from the API and the plugin daemon within
minutes.

## Upgrading Dify

Change `components.dify.chart.version` in `examples/helm/values.yaml`, then:

```bash
./scripts/gen-dify-secret-fields.py          # rewrite the placeholder key list
./scripts/gen-dify-secret-fields.py --check  # what a reviewer runs
```

Commit both. The Application refuses to render if the list was generated for a
different chart version, and the generator refuses if a new version puts a
placeholder anywhere other than a Secret's data.

## `helm upgrade` is no longer the install path

The Helm release that Dify's engineers installed (`sh.helm.release.v1.dify.v*`)
is still on the cluster, **but its recorded values are stale**: they predate the
credential rotation and the move from MinIO to ODF object storage. Running
`helm upgrade` with `helm get values` would put dead passwords and the old
MinIO endpoint back into the chart's Secrets. Change values in Git instead.

`scripts/render-dify-values.sh` and `scripts/fix-plugin-daemon-otlp.sh` remain
for a manual install on a cluster without this GitOps setup.

## What ArgoCD does not check

The 33 keys the Job owns. ArgoCD shows them as in sync whatever they hold; the
Job rewrites them from Git on every sync. Everything else in the chart —
including the other keys of the same objects — is compared and applied
normally.
